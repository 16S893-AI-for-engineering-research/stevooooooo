Notes on building this site with the pi coding agent — what worked, what didn't, and how the session activity broke down.

Agent session activity

Across every persisted pi session for this repository through today, here are the user messages, agent tool calls, and recorded model cost. Activity counts and cost use separate scales so the comparison remains readable.

Entry — 10/20/26 — Planning the robot software, and four bugs in a row

This was the switch from hardware to software I mentioned in the last entry. I described the robot to Pi as the orchestrator — two SO-101 arms that grip attachment points spaced 183.676 mm apart, a Rotrics DexArm carrying the print head and a line-laser scanner, everything on a fixed chassis with the printed tube being the thing that actually moves — and asked it to break the work into tasks small enough to hand to sub-agents.

It came back with 33 tasks across 7 milestones, carrying 227 acceptance criteria between them, ordered by dependency. Two of my own constraints changed the shape of the plan: the crawl cycle can't really be tested until the learned insertion works, so the real cycle depends on the policy task and a tube-free dry rehearsal comes first; and DexArm repeatability gets measured before the laser calibration, so the arm's own positioning error doesn't get quietly absorbed into the optical calibration and misattributed later.

Before writing any of it, Pi probed the machine instead of assuming: no /dev/ttyUSB* or /dev/video* in WSL, both arm adapters showing in usbipd as previously bound but not currently connected, and a 4 GB VRAM budget that constrains how the insertion policy can be trained. It also tried an actual usbipd attach, which failed on the permission check, which is how the one human-only task got justified rather than guessed at.

Keeping agents from quietly rewriting the requirements

I asked how we stop sub-agents from drifting — widening a tolerance, deleting a failing test, or ticking an acceptance criterion because the code looks about right. Checking turned up two real gaps: the project had no Definition of Done configured at all, and nothing told sub-agents not to edit criteria. Both are now closed. Every new task inherits six completion rules, including that criteria need evidence rather than code inspection and that criteria must not be altered to match whatever got built. Those rules live in a working-agreement spec and are wired into AGENTS.md, so any agent session loads them without being told.

There are now three specs: hardware truth, change control, and a live state-and-handoff doc. That last one exists because session transcripts are machine-local, lossy under compaction, and invisible to sub-agents — so the real memory has to live in the repo. A cold session reads three documents and knows where things stand, instead of replaying a long conversation.

Four bugs stacked behind one symptom

Then I accepted the hardware task and the walkthrough tab wouldn't open. It took four fixes, because each failure was hiding the next one: the guide launches with extensions disabled, which also unregistered the model provider, so the model couldn't resolve; then the launcher used wsl.exe --exec, which skips shell init, so the API key exported from .bashrc was missing; then the first crash had written a session entry with the provider recorded as literally "unknown", and because the runner resumes with --continue, every retry faithfully reloaded that poisoned session and died again; and finally the fallback script I was handed omitted the environment variable the extension uses to recognize a guide process, so /walk refused to run.

Worth recording honestly: Pi shipped three of those fixes without verifying the thing I actually cared about. It kept testing whether pi would start rather than whether the guide worked, and the real error only surfaced once it ran the guide command directly and captured stderr. It said as much afterward, and the last fix was verified end-to-end by asking the guide to read its own task queue before handing it back to me. It also corrected one of its earlier recommendations after testing proved it impossible — dropping the model flag couldn't work, because with extensions off there's no authenticated provider at all.

All of it is covered by 18 passing tests, plus documentation of the two startup failures that look identical but aren't. A side effect caught during staging: my Parley API key was sitting untracked in a repo that pushes to GitHub, one careless git add -A from being published. It's now ignored, along with the session artifacts and model checkpoints the robot work will start producing.

Entry — 10/19/26 — Human-only task handoffs

I added a workflow for assigning me tasks that only I can complete. The agent now has to justify why a task genuinely needs physical access, identity, authorization, or personal judgment, and it is supposed to minimize those requests rather than offload routine work. When a task is necessary, I explicitly accept a clear Backlog procedure with step-by-step actions, expected results, verification, and stop conditions. A single dedicated walkthrough tab can then guide me through accepted tasks one at a time, answer questions, record evidence, and return the result to the main agent for verification before work continues.

This project was super interesting. I don't believe the AI actually ever finished its thinking. It ran out of space twice. I think such stringent requirements in my prompt forced the AI to do alot more iterations than might have been totally necessary. Besides the AI, I noticed some of my own bias creeping in as a manager. This session most definitely ended in a cost overrun and technically the session wasn't even finished yet. This is partially because I found myself in a sunk cost fallacy. Since I couldn't actually know how much more progress there was to complete, I kept assuming that it was only a little bit more until eventaully I had spent $20.

AI's Take on What I Should Be Writing:

Asked the agent to rebuild the simulation from Jonckers et al. (2022), “Additive Manufacturing of Large Structures Using Free-Flying Satellites” — a free-flying satellite that 3D-prints trusses longer than itself. Full write-up and plots on the Simulation page. It reproduces 16 of 16 published quantities within tolerance.

The clarify-before-build skill earned its keep immediately. Before writing anything the agent asked six questions, and two of them changed the build: whether to model the robotic arm's full inverse kinematics (no — the paper treats it as an ideal follower) and how to handle the nozzle friction the paper never quantifies. I said "just use what they used" for friction, and it came back and told me plainly that the paper contains no friction number at all — only μ < 10-5 for the air bearing, which is a different thing entirely. So it calibrated against their reported 8.42 mm outcome instead and labelled it as calibrated rather than quietly presenting an invented number as a paper value. That is the behaviour I wanted: pushing back instead of fabricating.

It also pushed back on my 6-DoF question. I said if the paper used 6 DoF and it was needed for the plot, we had to do it. The agent checked and said no — ELISSA is a planar air-bearing table, the paper is explicitly 3 DoF, and 6 DoF appears only as future work. Saved a large amount of pointless effort.

Two things it found that I would have missed entirely. First, the paper's Figure 5 never dimensions which way the robotic arm is mounted, but the reported error split (0.68 mm in x versus 0.28 mm in y) only works if the arm points along the body y axis, because yaw error displaces the nozzle perpendicular to the mounting offset. It had the geometry backwards at first, got a symmetric error split, and used that mismatch to diagnose the orientation. Second, it thinks Equation 3 in the paper has a transposition — the matrix inverse is on the wrong side to compose correctly — and implemented the version that actually works while documenting the discrepancy rather than silently "fixing" it.

The hypothesis property tests paid off in a way example-based tests would not have. One test asserted that nozzle friction always produces a torque; hypothesis found a counterexample where travel is parallel to the lever arm and the torque is genuinely zero — correct physics, wrong test. Another exposed a real bug: the print was accidentally centred on the free-flyer's own centre of rotation, which cancelled the 400 mm lever arm to exactly zero and silently deleted the entire effect the paper is about. The simulation had been quietly reporting errors that were far too good.

Friction point worth recording: the sandbox had no PyPI access, so uv add pytest hypothesis failed outright. Rather than hand me an unrunnable test suite, the agent wrote a small vendored shim implementing just enough of both APIs to execute the real tests unmodified, plus a runner that uses the genuine libraries when the network allows. Same reason the figures are hand-emitted SVG instead of matplotlib — which ended up better for the site anyway, at 5–33 KB each and perfectly scalable.

Entry — Added a "clarify before build" skill

Directly in response to the animation-coaching problem below, I wrote a custom agent skill: .pi/skills/clarify-before-build/SKILL.md. It tells the agent that any time I ask it to build something with a physical or visible form — a website, an animation, a simulation, a diagram, anything where "it works" isn't the same as "it looks/moves right" — it must stop and ask clarifying questions about style, layout, motion, scope, and success criteria before writing any code, then restate the plan and get my go-ahead. The goal is to catch mismatches in what I imagined versus what gets built at the cheapest possible point (a question) instead of the most expensive point (a finished but wrong animation I have to debug in words).
