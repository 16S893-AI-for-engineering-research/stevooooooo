What's finished, in plain English

Every completed task, with what it does and why it matters. The small grey tags are the task IDs used in the repository.

M0 Foundations 4 of 4

  • One home for all robot code: a single package and one config file describing the hardware, so no task invents its own numbers. AA-4
  • Each device always has the same name: the two arms can never be mixed up after a reboot, which could drive one into the chassis. AA-5 AA-37
  • One camera at a time: all cameras share one USB 2.0 link, so code enforces that only one streams. AA-6
  • A flight recorder: every run leaves a log, so an unattended failure can be diagnosed afterwards. AA-7

M1 Hardware bring-up 3 of 8

  • Talking to the arm servos: a driver for the SO-101 servo bus and a map of which servo is which joint. AA-8
  • Talking to the DexArm: a driver for its G-code dialect that handles its quirks and reconnects safely. AA-12
  • Reading the cameras: capture from the mono cameras, skipping damaged frames instead of stopping the run. AA-14

M2 Geometry & coarse motion 4 of 8

  • A map of where everything is: the chassis stays still and the tube moves, so every attachment point is tracked as the tube advances. AA-15
  • Safe handover between code and AI: scripted motion hands control to the learned policy only inside strict limits, and always takes it back. AA-20
  • A gripper lock that holds: the gripper turns to a fixed 45° position to lock onto an attachment point, checked by eye on both arms. AA-17
  • The whole crawl cycle as an animation: both arms carry and regrip the tube on the robot model, so mistakes show up in pictures before the real arms move. AA-45

M3–M6 Insertion, crawl, leveling, autonomy 4 of 16

  • Robot-learning toolkit installed: LeRobot set up and connected to the SO-101 arms for recording demonstrations and training. AA-22
  • Recovering from bad cycles: detects a missed insertion, a latch that won't hold or a shifted tube, and gets back to a safe state. AA-28
  • Applying the leveling correction: the measured tilt and height of the part shift the DexArm's print frame before every section. AA-33
  • From slicer to printer: a DexArm profile in Cura, and checks that every sliced file stays inside the safe workspace. AA-34

Model checks & real-arm tests 7 of 12

  • A robot model I can trust: the collision model was compared with the real arms at the fold and marked verified. AA-40
  • Powered wrists and grippers: the encoder-only servos were replaced, calibrated, and every first powered move was watched and confirmed. AA-43 AA-48
  • True joint zeros: shoulder and elbow zeros measured from physical landmarks, so the model’s poses match the real arms. AA-47
  • Gripper lock checked on the real arms: repeated lock trials on both arms, all inside the expected band. AA-49
  • The full cycle on the real arms: both arms replay the animated cycle together, smoothly, at animation speed, without the tube. AA-50
  • Touching fold: at the printing pose each lower arm rests on its own shoulder, with the elbow torque capped. AA-52

Website & agent workflow 3 of 3

  • Interactive 3D CAD viewer of the real robot on this site, self-hosted so it works offline. AA-1 AA-3
  • Human-only task handoffs: when a step needs my hands or judgment, the agent writes a checked procedure and a separate tab guides me through it. AA-2

Hardware Nov 13, 2026

From animation to a full cycle on the real arms

An animation of the whole crawl cycle showed where the model was wrong; after fixing it, both real arms ran the full cycle smoothly.

Work done

  • Animation of the full crawl cycle on my cell model. It showed where the model and the real robot disagreed (the joint zero offsets and the fold pose). Both were fixed from landmark measurements, and the model’s bounds now match the robot well.AA-45
  • Shoulder and elbow zero landmarks measured on both arms.AA-47
  • Mesh collision model verified against the real fold.AA-40
  • New wrist servos calibrated, every powered move checked by me, and the 45° gripper position lock verified on both arms.AA-43 AA-48 AA-49
  • Whole cycle replayed live on both real arms, without the tube, moving smoothly at animation speed. After I confirm, the whole path is checked once in advance, and single bogus sensor readings are logged instead of aborting the run.AA-50
  • Touching fold: each lower arm now rests on its own shoulder at the printing pose, with elbow torque capped at 15%. It worked on the first supervised live run, at the start and end of the full cycle.AA-52

Notes

Have become much better at managing context and keeping cost down. Should look into making it a bit more automated.

Might have implemented too many checks. Progress is greatly slowed because of how many checks there are and how "safely" things are done. Could get more done taking more risk. For example, we don't need to abort because the servos get a sensor reading that was slightly too hot for one reading and then goes back to stable temperature.

Animation has worked really well at quickly identifying misunderstanding between reality and the current robot. Bounds are now matching well.

Another interesting thing is Claude considered the fact that I'm frustrated in weighing the validity of my wishes for less safety lol

Hardware Oct 27, 2026

Teaching AI the physical robot

Agents only understood the robot once I hand-built a clean robot model; the “broken” servos turned out to have no motors.

Work done

  • Hand-built URDF (a robot description file) of the whole cell: both arms with custom grippers and cameras, the DexArm with its laser camera, the base and the tube. It replaces raw CAD, whose duplicate part names confused the agents.
  • Collision checking: before any move, code checks the planned pose against this model and refuses if parts would touch. The DexArm check uses the arm's own firmware maths.AA-40
  • Servo mystery solved: wrist and gripper servos on both arms are encoder-only leader servos. Swap and recalibration planned.AA-43

Notes

Big lesson this week was that making AI understand something physical in real life is not easy. Especially when a model is as complicated as this is with 3 different robotic arms with many many parts, it has a hard time distinguishing things. I did not make it easier since alot of the parts in my model are named the same thing. Burned quite a bit of money on that mistake. Instead of just giving it the CAD, I ended up creating a urdf myself to give the agents. This made things much more understandable for it. I also realized I need more of one kind of the servo before I can complete everything and will need to rebuild the arms so that's fun. Went on a goose chase trying to figure that out, as well. Thought I had fried something but turned out they were dummy servos with just encoders so you could use them as a leader arm.

Planning the robot software

The whole robot was broken into 33 tasks with measurable pass/fail criteria before any code was written.

Work done

  • Described the system to the agent: two SO-101 arms gripping attachment points 183.7 mm apart, a DexArm with print head and laser, a fixed chassis and a moving tube.
  • 33 tasks, 7 milestones, 227 acceptance criteria.
  • Order matters: the crawl cycle can't be tested until learned insertion works, and DexArm repeatability is measured before laser calibration so arm error isn't mistaken for optical error.
  • Evidence rule: a criterion counts as done only with test output or a measurement, so agents can't quietly rewrite requirements to match what they built.
  • Getting the walkthrough tab to open took four separate fixes.

Simulation Sep 22, 2026

Recreating a paper’s simulation from scratch

A published free-flying 3D-printer simulation rebuilt in Python matches 16 of 16 reported numbers.

Work done

  • Rebuilt the simulation from Jonckers et al. (2022), “Additive Manufacturing of Large Structures Using Free-Flying Satellites”. Full write-up on the Simulation page.
  • Questions first: asking before building kept the scope right: no full arm kinematics, a planar 3 DoF model like the paper's, and nozzle friction clearly labelled as calibrated.
  • Found issues in the paper: the arm direction needed to match the reported error split, and one equation appears transposed. Both documented, not silently fixed.
  • Property-based tests caught one wrong test and one real bug (the print was centred on the wrong point, cancelling a 400 mm lever arm).

Notes

This project was super interesting. I don't believe the AI actually ever finished its thinking. It ran out of space twice. After that, I checked what it had written up to that point and it seemed complete but I think there is a good chance it would have continued working. I ulitmately decided not to try and let it finish because this project broke the $20 dollar mark in terms of tokens already. I think such stringent requirements in my prompt forced the AI to do alot more iterations than might have been totally necessary. Besides the AI, I noticed some of my own bias creeping in as a manager. This session most definitely ended in a cost overrun and technically the session wasn't even finished yet. This is partially because I found myself in a sunk cost fallacy. Since I couldn't actually know how much more progress there was to complete, I kept assuming that it was only a little bit more until eventaully I had spent $20.
